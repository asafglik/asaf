# מדריך התקנה: המעצב, מאגר התבניות ושרתי ההפקה

## 1. שלוש תת-מערכות

המערכת בנויה משלוש תת-מערכות:

| תת-מערכת | איפה רצה | מה עושה | מי משתמש |
|---|---|---|---|
| **1. המעצב** (`/`, `/designer.html`) | השרת המרכזי בענן | בניית תבניות: גרירה מעולם נתונים, ייבוא PDF/Word, וסוכן AI שממקם שדות, משפר את הטופס ומבצע שינויים לפי בקשה בכתב | המנהל (לכל הלקוחות), וכל לקוח שקיבל מפתח עיצוב (לתבניות שלו בלבד) |
| **2. מאגר התבניות** (`/repo.html`, `/api/repo/...`) | השרת המרכזי בענן | כל לקוח רואה ומוריד את התבניות שנבנו בשבילו, תבנית בודדת או חבילה. שרתי ההפקה מסתנכרנים ממנו לבד | לקוחות ושרתי ההפקה שלהם |
| **3. מנגנון ההפקה (runtime)** (`POST /api/render/...`) | השרת המרכזי, או שרת אצל הלקוח (`FD_MODE=render`) | מקבל תבנית ועולם נתונים (XML/JSON), ומחזיר PDF ו-metadata: מספר עמודים, אזהרות, ומיקום ונתונים של כל אזור חתימה ומילוי | המערכות של הלקוחות |

```
                    השרת המרכזי  https://forms.example.com
          ┌─────────────────────────────────────────────────────────┐
 מנהל ───▶│ 1. מעצב + סוכן AI   ──שמירה──▶  2. מאגר התבניות           │
 לקוח ───▶│    (מפתח עיצוב: רק התבניות שלו)     (תבניות לפי לקוח)       │
          │                                     │                   │
          │ 3. runtime מרכזי ◀── מערכת לקוח     │ סנכרון כל 5 דקות   │
          └─────────────────────────────────────┼───────────────────┘
                                                ▼  (מפתח ההפקה של הלקוח)
                                 3. runtime בשרת הלקוח  ◀── מערכת לקוח
                                    POST /api/render/1001 → PDF + metadata
```

### שלושה סוגי מפתחות

| מפתח | נוצר ב | מה מאפשר |
|---|---|---|
| **מפתח מנהל** (`FD_API_KEY`) | הגדרות השרת | הכול: המעצב לכל הלקוחות, מסך הלקוחות, המאגר של כל לקוח. נשאר רק אצלכם |
| **מפתח עיצוב** של לקוח | מסך ניהול ← לקוח ← עריכה | כניסה למעצב וליצירה ועריכה של התבניות של הלקוח בלבד. תבנית חדשה שהלקוח יוצר משויכת אליו אוטומטית. תבנית שמשותפת לכמה לקוחות פתוחה אצלו לקריאה בלבד, ואפשר לשכפל אותה. אין לו גישה למסך הלקוחות, לגופנים של כל המערכת או לתבניות של אחרים |
| **מפתח הפקה** (API) של לקוח | מסך ניהול ← לקוח ← עריכה | הפקה והורדה מהמאגר של התבניות של הלקוח בלבד. זה המפתח שמוגדר בשרתי ההפקה ובמערכות של הלקוח |

* בשרת נשמר רק ה-hash של כל מפתח. המפתח עצמו מוצג פעם אחת, כשיוצרים אותו.
* מפתח העיצוב ומפתח ההפקה של לקוח חייבים להיות שונים.

## 2. איך תבנית מגיעה ללקוח

1. **בונים את התבנית.** אפשר לבנות אותה בשתי דרכים:
   * **המנהל** בונה אותה ומשייך אותה ללקוח, בכרטיס הלקוח ← "תבניות", או ב-"+ שיוך" ליד התבנית;
   * **הלקוח** בונה אותה בעצמו עם מפתח העיצוב שלו, והיא משויכת אליו אוטומטית.
2. **ברגע שהתבנית נשמרת היא במאגר של הלקוח.** אין שלב "פרסום" נפרד.
3. **הלקוח מקבל אותה באחת משלוש דרכים:**
   * **הפקה מהשרת המרכזי:** `POST https://forms.example.com/api/render/<מספר>` עם מפתח ההפקה. השינוי נכנס לתוקף מיד.
   * **שרת הפקה משלו שמחובר למאגר:** השרת מוריד לבד כל תבנית חדשה או מעודכנת, בדיקה כל 5 דקות. רק תבניות שהשתנו יורדות, ותבנית שהוסרה מהלקוח נמחקת גם אצלו (סעיף 5).
   * **הורדה ידנית מהמאגר:** בדף "מאגר התבניות" (`/repo.html`) הלקוח מוריד תבנית בודדת (JSON) או חבילה של כל התבניות, ומתקין אותה בשרת שלו. שרת שאין לו גישה לאינטרנט מקבל את התבניות כך.

> **Runtime שמקבל את התבנית בקריאה:** אפשר גם לשלוח לשרת ההפקה את התבנית עצמה יחד עם הנתונים, בלי להתקין אותה קודם:
> `POST /api/render` עם `{ "template": { ...קובץ התבנית מהמאגר... }, "data": "<xml>...", "output": "json" }`.
> בשרת הפקה זה עובד עם כל מפתח תקין. בשרת המרכזי זה פתוח רק למפתח המנהל.

## 3. התקנה ראשונית של השרת המרכזי (Docker, מומלץ)

### מה צריך

* **שרת ענן עם Linux** (Ubuntu 22.04/24.04 למשל). לעומס של 1,000 קריאות במקביל וקובצי XML גדולים: 8 ליבות ו-16GB זיכרון. להתחלה מספיקות 4 ליבות ו-8GB.
* **דומיין** (למשל `forms.example.com`) שרשומת ה-DNS שלו (A) מפנה לכתובת ה-IP של השרת.
* **פורטים 80 ו-443 פתוחים** בחומת האש. הפורט 3700 לא נחשף החוצה.
* **Docker עם docker compose:**
  ```bash
  curl -fsSL https://get.docker.com | sh
  ```

### שלבים

```bash
# 1. מורידים את הקוד (או מעתיקים לשרת את התיקייה form-designer)
git clone https://github.com/asafglik/asaf.git
cd asaf/form-designer

# 2. הגדרות
cp deploy/.env.example deploy/.env
openssl rand -hex 32          # זה יהיה מפתח המנהל
nano deploy/.env              # DOMAIN=forms.example.com, FD_API_KEY=<המפתח שנוצר>,
                              # FD_MAX_CONCURRENT=<מספר הליבות>, ANTHROPIC_API_KEY (רשות, לסוכן החכם)

# 3. הפעלה
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d --build

# 4. בדיקה
curl https://forms.example.com/api/health
```

מה ה-compose מפעיל:

* **`form-designer`**
  * המעצב וה-API, עם Chromium מותקן בתוך ה-image.
  * התבניות, הלקוחות והגופנים נשמרים ב-volume בשם `fd-storage`, ונשארים גם אחרי עדכון או הפעלה מחדש.
  * השירות עולה מחדש לבד אם השרת מופעל מחדש.
* **`caddy`**
  * מוציא תעודת HTTPS לדומיין באופן אוטומטי (Let's Encrypt) ומעביר את הבקשות לשירות.
  * מוגדר לבקשות של עד 300MB ולהמתנה של עד 30 דקות, בשביל הפקות גדולות.

> **ייבוא Word "בפריסה מדויקת"** צריך LibreOffice. מגדירים `WITH_LIBREOFFICE=1` בקובץ `deploy/.env` ומריצים שוב את פקודת ההפעלה. ה-image גדל בכ-400MB.

### כניסה ראשונה

1. גולשים ל-`https://forms.example.com`. המערכת מבקשת את מפתח המנהל פעם אחת ושומרת אותו בדפדפן.
2. התבנית לדוגמה (#1001, חשבונית מס) כבר מותקנת, ואפשר לנסות עליה את המעצב.

### בלי Docker

אפשר גם להתקין ישירות:

1. מתקינים Node.js 22, Chromium (`apt install chromium`) ו-`git`.
2. מריצים:
   ```bash
   npm ci --omit=dev
   ```
3. מפעילים כשירות systemd עם `ExecStart=/usr/bin/node /opt/form-designer/server/index.js` ועם משתני הסביבה `FD_API_KEY`, `CHROME_PATH=/usr/bin/chromium` ו-`FD_MAX_CONCURRENT`.
4. מציבים לפניו Caddy או nginx בשביל HTTPS. ב-nginx מגדירים `client_max_body_size 300m;` ו-`proxy_read_timeout 1800s;`.

## 4. הקמת לקוח ושליחת תבנית אליו

1. **מסך ניהול ← לשונית "לקוחות" ← "+ לקוח חדש".** ממלאים שם וקוד לקוח.
2. **יוצרים לו מפתחות:**
   * **"יצירת מפתח"** יוצר את מפתח ההפקה: בשביל שרתי ההפקה, המערכות של הלקוח והמאגר.
   * **"יצירת מפתח עיצוב"** יוצר את מפתח העיצוב, רק אם הלקוח יעצב תבניות בעצמו.

   כל מפתח מועתק ללוח כשיוצרים אותו. שולחים אותו ללקוח בערוץ מאובטח. הוא לא יוצג שוב: אם הוא אבד, יוצרים מפתח חדש, והישן מפסיק לעבוד.
3. **בונים או מייבאים תבנית** במעצב:
   * טוענים עולם נתונים (דוגמת XML או JSON של הלקוח).
   * גוררים שדות, טבלאות ואזורי חתימה.
   * שומרים עם מספר תבנית.
4. **משייכים את התבנית ללקוח**, באחת משתי הדרכים:
   * בכרטיס הלקוח: **"תבניות"** ← מסמנים את התבנית ← "שמירה";
   * או ברשימת התבניות: **"+ שיוך"** ליד התבנית.

   תבנית אחת יכולה להיות משויכת לכמה לקוחות.
5. **שולחים ללקוח את פרטי החיבור:**
   * הכתובת: `https://forms.example.com/api/render/<מספר תבנית>`;
   * המפתח שלו;
   * מבנה הנתונים (דוגמת ה-XML שעליה התבנית בנויה).

### לקוח שמעצב בעצמו

* הלקוח גולש ל-`https://forms.example.com`, מזין את מפתח העיצוב פעם אחת, ורואה רק את התבניות שלו.
* כפתור **"החלפת מפתח"** בפינה מנקה את המפתח מהדפדפן.
* יש לו את כל המעצב, כולל סוכן ה-AI. כל תבנית שהוא שומר נכנסת למאגר שלו.

### סוכן ה-AI במעצב

בלשונית **סוכן ✨** במעצב:

| פעולה | מה הסוכן מקבל | מה הוא עושה |
|---|---|---|
| **טופס חדש מעולם הנתונים** | XML/JSON בלבד | בונה טופס שלם: כותרת, קבוצות של שדות עם תוויות בעברית, טבלאות לרשימות עם סיכומים, כותרת תחתונה ואזור חתימה |
| **עיצוב אוטומטי מקובץ דוגמה** | PDF או Word של טופס קיים, ועולם הנתונים | ממקם שדות, טבלאות, תיבות סימון ואזורי חתימה מעל הדוגמה, או בונה את המסמך מחדש מרכיבים |
| **חוות דעת על טופס קיים** | PDF שהמערכת הנוכחית הפיקה | ציון, חולשות ושיפורים, מיפוי של כל ערך לשדה בעולם הנתונים, ובנייה של גרסה משופרת |
| **שיפור הטופס הנוכחי** | התבנית הפתוחה | יישור לרשת, ריווח, היררכיה וקריאות, בלי לשנות שדות וקישורים |
| **בקשות בכתב** | למשל "הוסף כותרת תחתונה עם מספרי עמודים" | מבצע את השינוי. כל תשובה היא פעולה אחת שאפשר לבטל |

* הסוכן משתמש ב-Claude ודורש `ANTHROPIC_API_KEY` בשרת המרכזי. בשרתי ההפקה הוא לא נדרש.
* **בלי מפתח** עדיין עובדים:
  * בניית טופס בסיסי מעולם הנתונים, כשהתוויות הן שמות השדות;
  * זיהוי בסיסי של שדות בקובץ דוגמה.
* **קובץ Word כדוגמה** מומר ל-PDF עם LibreOffice, אם הוא מותקן (`WITH_LIBREOFFICE=1`). בלי LibreOffice, קובץ docx מומר לפי התוכן שלו.

### מה הלקוח מריץ

```bash
curl -X POST "https://forms.example.com/api/render/1001" \
  -H "x-api-key: <מפתח הלקוח>" \
  -H "Content-Type: application/xml" \
  --data-binary @invoice.xml -o invoice.pdf
```

* **מסמך בודד:**
  * `?output=json` מחזיר את ה-PDF ב-base64, יחד עם המיקום והנתונים של כל אזור חתימה ומילוי.
  * `?lang=en` מפיק את המסמך באנגלית.
* **כמויות גדולות:** `POST /api/render-batch/1001` עם `{"records":[...]}`. מוחזר ZIP עם PDF לכל רשומה.
* **רשימת התבניות של הלקוח:** `GET /api/templates` עם המפתח שלו.
* **קוד לדוגמה** בתיקייה `clients/`:
  * Caché/IRIS: `FormDesigner.Client.cls`;
  * C#: `RenderClient.cs`;
  * PowerShell: `render.ps1`.

  בכל הדוגמאות מעבירים את המפתח בכותרת `x-api-key`.

### עדכון תבנית שהלקוח כבר משתמש בה

* **השמירה במעצב משפיעה על ההפקה של הלקוח מיד.**
* **לשינוי גדול:**
  1. משכפלים את התבנית ("שכפול") ועובדים על העותק.
  2. בודקים אותו עם נתוני הלקוח (תצוגה מקדימה במעצב).
  3. משייכים את העותק ללקוח, או מעתיקים את העיצוב לתבנית המקורית.
* **חזרה לגרסה קודמת:** לכל תבנית נשמרות 20 הגרסאות האחרונות.

## 5. שרת הפקה (runtime) אצל הלקוח

על שרת Linux של הלקוח, עם Docker:

```bash
git clone https://github.com/asafglik/asaf.git && cd asaf/form-designer
cat > deploy/.env <<EOF
FD_REPO_URL=https://forms.example.com
FD_REPO_KEY=<מפתח ההפקה של הלקוח>
FD_MAX_CONCURRENT=4
EOF
docker compose -f deploy/docker-compose.render.yml --env-file deploy/.env up -d --build
```

* **סנכרון:**
  * השרת מתחבר למאגר מיד כשהוא עולה, ואחר כך כל `FD_REPO_SYNC_MINUTES` (ברירת מחדל 5).
  * הוא מוריד רק תבניות חדשות או מעודכנות, כולל גופנים שהועלו ושהתבניות משתמשות בהם.
  * תבניות שהוסרו מהלקוח נמחקות גם אצלו.
  * אם המאגר לא זמין, התבניות שכבר מותקנות ממשיכות לעבוד.
* **המפתח:** אותו מפתח הפקה משמש גם לסנכרון וגם להפקה. השרת מקבל אותו אוטומטית, בלי הגדרה נוספת.
* **כמה לקוחות על שרת אחד:** `FD_REPO_KEY` מקבל כמה מפתחות מופרדים בפסיק.
* **הפקה:** מערכות הלקוח קוראות ל-`http://<שרת>:3700/api/render/<מספר>` עם מפתח ההפקה, בדיוק כמו בשרת המרכזי.
* **בדיקת מצב:**
  * `GET /api/repo/status` עם מפתח המנהל של שרת ההפקה (`FD_API_KEY` שלו) מחזיר את הסנכרון האחרון ואת התבניות שמותקנות.
  * `POST /api/repo/sync` מסנכרן מיד.
  * `node cli/sync.js` מסנכרן פעם אחת משורת הפקודה.
* **בלי חיבור למאגר** (רשת סגורה):
  1. מורידים חבילה מדף המאגר.
  2. מעתיקים אותה ל-`deploy/bundles`.
  3. מתקינים אותה:
     ```bash
     docker compose -f deploy/docker-compose.render.yml exec form-render \
       node cli/import-bundle.js /bundles/bundle-customer-3.json --prune
     ```

  אפשר גם להעלות אותה ב-`POST /api/repo/install` עם מפתח המנהל של שרת ההפקה.
* **Proxy:** אם השרת יוצא לאינטרנט דרך proxy, מגדירים `HTTPS_PROXY` יחד עם `NODE_USE_ENV_PROXY=1`. זה נתמך ב-Node 22.21 ומעלה.
* **Windows בלי Docker:**
  1. מתקינים Node.js 22 ו-Chrome או Edge.
  2. מריצים `npm ci --omit=dev`.
  3. מגדירים את משתני הסביבה `FD_MODE=render`, `FD_REPO_URL` ו-`FD_REPO_KEY`.
  4. מפעילים כשירות עם [NSSM](https://nssm.cc):
     ```
     nssm install FormRender "C:\Program Files\nodejs\node.exe" "C:\form-designer\server\index.js"
     ```

## 6. תפעול

### עדכון גרסה

```bash
git pull && docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d --build
```

התבניות והלקוחות נשמרים ב-volume, כך שהעדכון לא נוגע בהם.

### גיבוי

כל המידע נמצא ב-volume `fd-storage`: התבניות (קובץ JSON לכל תבנית, כולל תמונות ו-PDF מקור), הלקוחות והגופנים. כדאי לגבות אותו פעם ביום:

```bash
docker run --rm -v deploy_fd-storage:/s -v $PWD:/b alpine tar czf /b/fd-backup-$(date +%F).tgz -C /s .
```

(שם ה-volume המדויק מופיע ב-`docker volume ls`.)

### בדיקות שוטפות

* **לוג:**
  ```bash
  docker compose -f deploy/docker-compose.yml logs -f form-designer
  ```
* **מצב השירות:** `GET /api/health`. Docker מסמן את השירות כ-`healthy` לפי הבדיקה הזו.
* **בדיקת עומס** על השרת שלכם:
  ```bash
  node scripts/loadtest.js --url https://forms.example.com --template 1001 --data examples/invoice.xml --count 1000 --key <מפתח>
  ```

## 7. אבטחה (רשימת בדיקה)

* מפתח המנהל ארוך ואקראי (`openssl rand -hex 32`), ולא נמסר ללקוחות.
* הגישה לשרת רק ב-HTTPS (Caddy), והפורט 3700 לא חשוף לאינטרנט.
* מפתחות נפרדים לכל לקוח: מפתח הפקה, ומפתח עיצוב רק למי שמעצב. לקוח שעוזב: מוחקים אותו, או מסירים את המפתחות שלו בעריכת הלקוח.
* אם אין לקוחות שמעצבים בעצמם, אפשר להגביל את המעצב לרשת המשרד. ב-Caddy חוסמים לפי כתובת IP את כל הנתיבים, ומשאירים פתוחים רק את `/api/render*`, `/api/render-batch*`, `/api/templates`, `/api/repo/*`, `/api/me`, `/api/health`, ואת דף המאגר וקבציו (`/repo.html`, `/js/*`, `/css/*`, `/shared/*`, `/fonts*`).
* בזמן ההפקה הדפדפן לא ניגש לרשת ו-JavaScript כבוי, כך שנתונים מהלקוח לא יכולים להריץ קוד או לפנות לשרתים אחרים.
* יש גיבוי יומי של ה-volume.
