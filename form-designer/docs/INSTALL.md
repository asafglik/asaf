# מדריך התקנה: שרת ענן מרכזי ו-API הפקה לכל לקוח

המדריך מסביר איך להקים את המערכת כך ששרת ענן אחד מחזיק את המעצב, לכל לקוח יש API הפקה משלו, וכל תבנית נשלחת ללקוח שהיא שייכת לו.

## 1. מה יש במערכת

| חלק | מה הוא עושה | מי משתמש בו |
|---|---|---|
| **מסך ניהול** (`/`) | רשימת התבניות והלקוחות, שיוך תבניות ללקוחות, מפתחות API | צוות העיצוב (אתם) |
| **מעצב** (`/designer.html`) | בניית תבנית על עולם נתונים (XML/JSON), ייבוא מ-PDF או Word, סוכן עיצוב חכם | צוות העיצוב |
| **API הפקה** (`POST /api/render/{מספר תבנית}`) | מקבל XML/JSON ומחזיר PDF, כולל מיקום אזורי החתימה והמילוי | מערכות של הלקוחות |
| **הפקה בכמויות** (`POST /api/render-batch/{מספר תבנית}`) | אלפי מסמכים בקריאה אחת, ZIP או PDF מאוחד | מערכות של הלקוחות |

### שני מפתחות, שתי הרשאות

* **מפתח מנהל** (`FD_API_KEY`) נותן גישה למעצב, למסך הניהול ולכל התבניות. הוא נשאר רק אצלכם.
* **מפתח לקוח** נוצר במסך הניהול, אחד לכל לקוח.
  * הוא מאפשר רק להפיק את התבניות שמשויכות לאותו לקוח, ולראות את הרשימה שלהן.
  * הוא לא נותן גישה למעצב, ולא לתבניות של לקוחות אחרים.
  * בשרת נשמר רק ה-hash של המפתח. המפתח עצמו מוצג פעם אחת, כשיוצרים אותו.

## 2. איך התבנית "נשלחת" ללקוח

יש שתי דרכים לחבר לקוח. אפשר לשלב ביניהן: רוב הלקוחות בשרת המרכזי, ולקוחות מסוימים עם שרת משלהם.

### דרך א (מומלצת): כל הלקוחות מפיקים מהשרת המרכזי

```
                         שרת ענן אחד  https://forms.example.com
                 ┌──────────────────────────────────────────────┐
 צוות העיצוב ───▶│ מעצב + מסך ניהול          (מפתח מנהל)        │
                 │                                              │
 מערכת לקוח א ──▶│ POST /api/render/1001      (מפתח של לקוח א)  │──▶ PDF
 מערכת לקוח ב ──▶│ POST /api/render/2001      (מפתח של לקוח ב)  │──▶ PDF
                 │ storage: תבניות, לקוחות, גופנים               │
                 └──────────────────────────────────────────────┘
```

* **"שליחת" תבנית ללקוח היא שיוך שלה ללקוח במסך הניהול.** מאותו רגע הלקוח יכול להפיק אותה עם המפתח שלו.
* **שינוי בתבנית נכנס לתוקף מיד בשמירה.** אין צורך להתקין אצל הלקוח שום דבר.
* לקוח שינסה להפיק תבנית שאינה שלו יקבל `403`.

### דרך ב: ללקוח יש שרת הפקה משלו

מתאים ללקוח שהנתונים שלו לא יוצאים מהרשת שלו.

```
 שרת ענן (מעצב)  ──  חבילת התקנה (JSON)  ──▶  שרת הפקה אצל הלקוח (FD_MODE=render)
                                                ▲
                                   מערכת הלקוח ─┘  POST /api/render/1001  (מפתח הלקוח)
```

* בשרת המרכזי לוחצים על **"חבילת התקנה"** בכרטיס הלקוח. מורד קובץ אחד עם כל התבניות של הלקוח, כולל ה-hash של המפתח שלו.
* בשרת הלקוח מתקינים את הקובץ בפקודה אחת (ראו סעיף 5).
* אחרי כל שינוי בתבנית מורידים חבילה חדשה ומתקינים אותה שוב.
* בשרת כזה אין מעצב. יש בו רק API להפקה, והמפתח של הלקוח עובד בו כמו בשרת המרכזי.

## 3. התקנה ראשונית של השרת המרכזי (Docker, מומלץ)

### מה צריך

* **שרת ענן עם Linux** (Ubuntu 22.04/24.04 למשל). לעומס של 1,000 קריאות במקביל וקובצי XML גדולים: 8 ליבות ו-16GB זיכרון. להתחלה מספיקות 4 ליבות ו-8GB.
* **דומיין** (למשל `forms.example.com`) שרשומת ה-DNS שלו (A) מפנה לכתובת ה-IP של השרת.
* **פורטים 80 ו-443 פתוחים** בחומת האש. הפורט 3700 לא נחשף החוצה.
* **Docker עם docker compose:**
  ```bash
  curl -fsSL https://get.docker.com | sh
  ```

### שלבים

```bash
# 1. מורידים את הקוד (או מעתיקים לשרת את התיקייה form-designer)
git clone https://github.com/asafglik/asaf.git
cd asaf/form-designer

# 2. הגדרות
cp deploy/.env.example deploy/.env
openssl rand -hex 32          # זה יהיה מפתח המנהל
nano deploy/.env              # DOMAIN=forms.example.com, FD_API_KEY=<המפתח שנוצר>,
                              # FD_MAX_CONCURRENT=<מספר הליבות>, ANTHROPIC_API_KEY (רשות, לסוכן החכם)

# 3. הפעלה
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d --build

# 4. בדיקה
curl https://forms.example.com/api/health
```

מה ה-compose מפעיל:

* **`form-designer`**
  * המעצב וה-API, עם Chromium מותקן בתוך ה-image.
  * התבניות, הלקוחות והגופנים נשמרים ב-volume בשם `fd-storage`, ונשארים גם אחרי עדכון או הפעלה מחדש.
  * השירות עולה מחדש לבד אם השרת מופעל מחדש.
* **`caddy`**
  * מוציא תעודת HTTPS לדומיין באופן אוטומטי (Let's Encrypt) ומעביר את הבקשות לשירות.
  * מוגדר לבקשות של עד 300MB ולהמתנה של עד 30 דקות, בשביל הפקות גדולות.

> **ייבוא Word "בפריסה מדויקת"** צריך LibreOffice. מגדירים `WITH_LIBREOFFICE=1` בקובץ `deploy/.env` ומריצים שוב את פקודת ההפעלה. ה-image גדל בכ-400MB.

### כניסה ראשונה

1. גולשים ל-`https://forms.example.com`. המערכת מבקשת את מפתח המנהל פעם אחת ושומרת אותו בדפדפן.
2. התבנית לדוגמה (#1001, חשבונית מס) כבר מותקנת, ואפשר לנסות עליה את המעצב.

### בלי Docker

אפשר גם להתקין ישירות:

1. מתקינים Node.js 22, Chromium (`apt install chromium`) ו-`git`.
2. מריצים:
   ```bash
   npm ci --omit=dev
   ```
3. מפעילים כשירות systemd עם `ExecStart=/usr/bin/node /opt/form-designer/server/index.js` ועם משתני הסביבה `FD_API_KEY`, `CHROME_PATH=/usr/bin/chromium` ו-`FD_MAX_CONCURRENT`.
4. מציבים לפניו Caddy או nginx בשביל HTTPS. ב-nginx מגדירים `client_max_body_size 300m;` ו-`proxy_read_timeout 1800s;`.

## 4. הקמת לקוח ושליחת תבנית אליו

1. **מסך ניהול ← לשונית "לקוחות" ← "+ לקוח חדש".** ממלאים שם וקוד לקוח.
2. **לוחצים "יצירת מפתח".** המפתח נוצר ומועתק ללוח.
   * שולחים אותו ללקוח בערוץ מאובטח.
   * הוא לא יוצג שוב. אם הוא אבד, יוצרים מפתח חדש, והישן מפסיק לעבוד.
3. **בונים או מייבאים תבנית** במעצב:
   * טוענים עולם נתונים (דוגמת XML או JSON של הלקוח).
   * גוררים שדות, טבלאות ואזורי חתימה.
   * שומרים עם מספר תבנית.
4. **משייכים את התבנית ללקוח**, באחת משתי הדרכים:
   * בכרטיס הלקוח: **"תבניות"** ← מסמנים את התבנית ← "שמירה";
   * או ברשימת התבניות: **"+ שיוך"** ליד התבנית.

   תבנית אחת יכולה להיות משויכת לכמה לקוחות.
5. **שולחים ללקוח את פרטי החיבור:**
   * הכתובת: `https://forms.example.com/api/render/<מספר תבנית>`;
   * המפתח שלו;
   * מבנה הנתונים (דוגמת ה-XML שעליה התבנית בנויה).

### מה הלקוח מריץ

```bash
curl -X POST "https://forms.example.com/api/render/1001" \
  -H "x-api-key: <מפתח הלקוח>" \
  -H "Content-Type: application/xml" \
  --data-binary @invoice.xml -o invoice.pdf
```

* **מסמך בודד:**
  * `?output=json` מחזיר את ה-PDF ב-base64, יחד עם המיקום והנתונים של כל אזור חתימה ומילוי.
  * `?lang=en` מפיק את המסמך באנגלית.
* **כמויות גדולות:** `POST /api/render-batch/1001` עם `{"records":[...]}`. מוחזר ZIP עם PDF לכל רשומה.
* **רשימת התבניות של הלקוח:** `GET /api/templates` עם המפתח שלו.
* **קוד לדוגמה** בתיקייה `clients/`:
  * Caché/IRIS: `FormDesigner.Client.cls`;
  * C#: `RenderClient.cs`;
  * PowerShell: `render.ps1`.

  בכל הדוגמאות מעבירים את המפתח בכותרת `x-api-key`.

### עדכון תבנית שהלקוח כבר משתמש בה

* **השמירה במעצב משפיעה על ההפקה של הלקוח מיד.**
* **לשינוי גדול:**
  1. משכפלים את התבנית ("שכפול") ועובדים על העותק.
  2. בודקים אותו עם נתוני הלקוח (תצוגה מקדימה במעצב).
  3. משייכים את העותק ללקוח, או מעתיקים את העיצוב לתבנית המקורית.
* **חזרה לגרסה קודמת:** לכל תבנית נשמרות 20 הגרסאות האחרונות.

## 5. שרת הפקה אצל הלקוח (דרך ב)

על שרת Linux של הלקוח, עם Docker:

```bash
git clone https://github.com/asafglik/asaf.git && cd asaf/form-designer
docker compose -f deploy/docker-compose.render.yml up -d --build

# מעתיקים את חבילת ההתקנה שהורדה מהשרת המרכזי לתיקייה deploy/bundles ומתקינים:
docker compose -f deploy/docker-compose.render.yml exec form-render \
  node cli/import-bundle.js /bundles/bundle-customer-3.json
```

* השרת מאזין בפורט 3700 ברשת של הלקוח. מערכות הלקוח קוראות ל-`http://<שרת>:3700/api/render/<מספר>` עם המפתח שלהן, בדיוק כמו בשרת המרכזי.
* **עדכון תבניות:** מורידים חבילה חדשה ומריצים שוב את פקודת ה-`import-bundle`. אין צורך להפעיל את השרת מחדש.
* **Windows בלי Docker:**
  1. מתקינים Node.js 22 ו-Chrome או Edge.
  2. מריצים `npm ci --omit=dev`.
  3. מריצים `node cli/import-bundle.js bundle-customer-3.json`.
  4. מפעילים כשירות עם [NSSM](https://nssm.cc):
     ```
     nssm install FormRender "C:\Program Files\nodejs\node.exe" "C:\form-designer\server\index.js --mode=render"
     ```

## 6. תפעול

### עדכון גרסה

```bash
git pull && docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d --build
```

התבניות והלקוחות נשמרים ב-volume, כך שהעדכון לא נוגע בהם.

### גיבוי

כל המידע נמצא ב-volume `fd-storage`: התבניות (קובץ JSON לכל תבנית, כולל תמונות ו-PDF מקור), הלקוחות והגופנים. כדאי לגבות אותו פעם ביום:

```bash
docker run --rm -v deploy_fd-storage:/s -v $PWD:/b alpine tar czf /b/fd-backup-$(date +%F).tgz -C /s .
```

(שם ה-volume המדויק מופיע ב-`docker volume ls`.)

### בדיקות שוטפות

* **לוג:**
  ```bash
  docker compose -f deploy/docker-compose.yml logs -f form-designer
  ```
* **מצב השירות:** `GET /api/health`. Docker מסמן את השירות כ-`healthy` לפי הבדיקה הזו.
* **בדיקת עומס** על השרת שלכם:
  ```bash
  node scripts/loadtest.js --url https://forms.example.com --template 1001 --data examples/invoice.xml --count 1000 --key <מפתח>
  ```

### קיבולת

| | |
|---|---|
| **קצב** | בערך 4 מסמכים בשנייה לכל ליבה (חשבונית של עמוד אחד). מגדירים `FD_MAX_CONCURRENT` כמספר הליבות |
| **עומס** | 1,000 קריאות בו-זמנית ממתינות בתור ומקבלות תשובה לפי הסדר. ללקוחות כדאי להגדיר timeout של כמה דקות |
| **קבצים גדולים** | XML/JSON של עד 50MB בקריאה. שרת שמקבל הרבה קבצים גדולים במקביל צריך 16GB זיכרון |
| **הגדרות נוספות** | בטבלת ההגדרות ב-[README](../README.md#הגדרות) |

## 7. אבטחה (רשימת בדיקה)

* מפתח המנהל ארוך ואקראי (`openssl rand -hex 32`), ולא נמסר ללקוחות.
* הגישה לשרת רק ב-HTTPS (Caddy), והפורט 3700 לא חשוף לאינטרנט.
* מפתח נפרד לכל לקוח. לקוח שעוזב: מוחקים אותו, או מסירים את המפתח שלו בעריכת הלקוח.
* כדי להגביל את המעצב לרשת המשרד, אפשר להגדיר ב-Caddy חסימה לפי כתובת IP לכל הנתיבים, חוץ מ-`/api/render*`, `/api/render-batch*`, `/api/templates` ו-`/api/health`, שנשארים פתוחים ללקוחות.
* בזמן ההפקה הדפדפן לא ניגש לרשת ו-JavaScript כבוי, כך שנתונים מהלקוח לא יכולים להריץ קוד או לפנות לשרתים אחרים.
* יש גיבוי יומי של ה-volume.
